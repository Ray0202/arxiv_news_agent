现有 LLM agent 的表现不只取决于 base model，也卡在 harness；但 harness 主要靠人工调，换模型就得重做，扩展性很差。摘要里没有给出统一的失败模式刻画，只强调不同模型的行为差异会让 harness 高度 model-specific。

Self-Harness 把改 harness 这件事做成三步迭代：先从 execution traces 里做 Weakness Mining，找模型特有的失败模式；再用 Harness Proposal 生成尽量小、但和这些失败绑定的改动；最后靠 Proposal Validation 做 regression testing，只接受不过拟合旧错误的候选编辑。核心不是更强的外部 agent，而是让同一个 agent 在最小初始 harness 上自我修补。

作者把它放到 Terminal-Bench-2.0、SWE-bench Verified 和 AppWorld 上测，基座模型是 MiniMax M2.5、Qwen3.5-35B-A3B 和 GLM-5。摘要声称九个 model-benchmark 组合里，最终 harness 的 held-in 和 held-out pass rate 都提升了，整体相对增益最高到 $132 ext{%}$。

这类结果说明，harness 不只是固定脚手架，也可以被当成可学习对象；至少在这三个 benchmark 和这三个模型上，改动确实朝着 artifact handling、runtime control、software-patch verification 和 application-state retrieval 这些瓶颈去了。但摘要只给了整体趋势，没有看到每个组合的绝对值、消融或回归测试细节，所以还不能判断它对更开放环境、更多模型族是否同样稳。

LLM agents are bottlenecked not just by the base model, but by the harness that mediates action, feedback, and state handling. In current practice that harness is hand-engineered, so it does not scale when models change behavior or new models arrive.

Self-Harness turns harness design into a loop the agent runs on itself. It mines failure patterns from execution traces, proposes minimal edits tied to those failures, and then validates each candidate with regression testing before keeping it. The point is not to summon a stronger external agent, but to let the same agent refine its own operating scaffold.

The abstract says they tested this on Terminal-Bench-2.0, SWE-bench Verified, and AppWorld, using MiniMax M2.5, Qwen3.5-35B-A3B, and GLM-5. Across all nine model-benchmark combinations, the final harness improved both held-in and held-out pass rates, with overall relative gains reaching $132 ext{%}$. The retained edits were said to target benchmark-specific bottlenecks in artifact handling and runtime control, software-patch verification, and application-state retrieval.

The main takeaway is that harnesses can be treated as adaptive objects, not fixed wrappers. But this is still abstract-only evidence: there are no absolute scores, no ablations, and no detail on how strong the regression tests were or how many edits survived them. So the claim looks plausible and practically relevant, but its robustness beyond these three benchmarks and three model families remains unshown.

现有 agent memory 多在追 recall：把相关片段捞出来，却不管后续 session 已经把它覆盖了。于是会出现 state drift，答案里明明带着旧值，模型却按旧值行动。作者把缺口从“找不找得到”拆成“当前到底谁生效”，把 state tracking 定为与 recall 不同的能力。

关键动作是把记忆改成 state-first。StateMemBench 用 symbolic event program 生成多 session 场景，把 facts、rules 和 derived quantities 的 supersession 与依赖写死，再用 closed-pool 评分区分 drift、off-pool 和其他错误。StateMem 先把每轮对话解析成 state units，再在更新时显式标记 superseded，并沿依赖图 $G=(U,E)$ 做 deterministic recheck；回答时只对活跃状态重算。

在 $234$ 个场景上，长上下文、retrieval 和现有 memory baseline 都被这些陷阱压住。DeepSeek-V4-Flash 上，StateMem 准确率 $0.363$，高于最强同骨干基线 $0.205$；Qwen-3.5-9B 上是 $0.233$ 对 $0.149$。作为 wrapper，它在 $6$ 个 backend 上还能带来 $+31.7$ 到 $+66.6$ 个点，其中 $+15.0$ 到 $+31.7$ 个点来自状态结构本身。

这说明 state tracking 不是 recall 的副产物，而是可以单独设计、单独评测的能力；显式状态结构确实有用，但前提是答题模型不能太弱。它的短板也明显：salience 仍然很吃力，而且 StateMemBench 的冲突是人为构造、closed-pool 的，测得更像受控状态维护，不是开放世界记忆。

Most agent memory work chases recall: can the system surface the right snippet? That misses state drift, where the relevant fact is present but the agent acts on an outdated value after later revisions. The paper argues the real gap is not retrieval but maintaining the currently operative state across sessions.

The trick is to make state a first-class object. StateMemBench generates multi-session scenarios from symbolic event programs, with explicit supersession and dependency structure, then scores closed-pool answers so drift is separated from generic errors. StateMem parses each turn into state units, marks units as superseded, propagates invalidation over a dependency graph $G=(U,E)$, and asks the model to recompute only from the surviving state.

On $234$ scenarios, existing memory, retrieval, and long-context baselines struggle. StateMem reaches $0.363$ on DeepSeek-V4-Flash, up from $0.205$ for the strongest same-backbone baseline, and $0.233$ on Qwen-3.5-9B versus $0.149$ for the strongest memory system. As a wrapper, the same state tracing adds $31.7$ to $66.6$ points over $6$ backends on StateMemBench, with $15.0$ to $31.7$ points attributed to structure rather than extra text.

The main takeaway is that state tracking is a separable capability, not a side effect of better recall. But the wins are uneven: salience remains weak on the Qwen backbone, and the wrapper can beat the full persistent system when the transcript still fits in context. The benchmark also uses explicit, closed-pool conflicts, so it measures controlled state maintenance more cleanly than messy real-world memory.

方法Method

core idea
StateMem 把多轮记忆表示成 state units，每个 unit 记录 $id$、content、priority、source 和 $deps$。输入阶段每轮一次 LLM 抽取，更新阶段先做 supersession，再沿依赖图 $G=(U,E)$ 做 deterministic recheck；测试时把活跃状态渲染成结构块 $\mathcal{S}$，再用一轮 LLM 只对当前有效状态重算答案。这样把“谁被覆盖了、谁还有效”从生成模型里拆开。
StateMem represents multi-turn memory as state units, each with $id$, content, priority, source, and $deps$. Ingestion uses one LLM call per turn to extract units, update applies supersession and then runs a deterministic recheck over the dependency graph $G=(U,E)$; test time renders the active state as a structured block $\mathcal{S}$ and uses one more LLM call to recompute the answer from current state only. The point is to separate “what was overwritten” from “what is still in force.”
architecture
TurnEncoder -> StateStore -> Rechecker on $G=(U,E)$ -> render $\mathcal{S}$ -> answer call; $u=(id,content,priority,source,deps)$, $priority\in\{hard,soft\}$, $deps\in\{derived\_from,coupled\_with\}$
data
StateMemBench: $234$ multi-session scenarios; Set A $190$ single-probe scenarios, $18$ sessions each ($\sim165$ turns, $\sim3$k tokens); Set B $44$ fused scenarios, $\sim38$ sessions each ($\sim599$ turns, $\sim7$-$15$k tokens). Domains: research, shopping, personal finance. Also evaluated on LongMemEval ($n=500$, $k=20$) and LoCoMo ($n=1,985$).

Time-series pretraining still breaks at tokenization. Dataset-specific patch sizes plus separate FFNs fracture the representation space, while a globally fixed small patch creates bottlenecks and washes out local dynamics. The model is forced to choose between cross-dataset compatibility and within-series fidelity.

SATS makes patch size an explicit scale. It keeps scale-specific FFNs, pools tokens by patch size into $Y\in\mathbb{R}^{N\times D}$, and applies a scale-aware alignment loss that pulls mean prototypes together and pushes max anchors apart: $\mathcal{L}_{\text{sa}}=\mathcal{L}_{\text{close}}+\beta\mathcal{L}_{\text{far}}$, with $\mathcal{L}=\mathcal{L}_{\text{nll}}+\alpha\mathcal{L}_{\text{sa}}$. On top of that, hybrid masking alternates random and contiguous spans so reconstruction has to learn both local completion and long-range structure.

The experiments cover LSTF, GIFT-Eval, and Monash after pretraining on LOTSA. On zero-shot LSTF, SATS_B reaches 0.316 MSE versus 0.348 for Moirai_B, a 9.2% reduction, and the 14M SATS_S still tops the average table. In the GIFT-Eval ablation, removing SA degrades MASE/CRPS from 0.802/0.550 to 0.866/0.607, which is consistent with the alignment story.

The boundary is clear: this is a patch-based encoder pretraining recipe, not a universal masking trick. HM does not transfer to decoder-only training, very small patches hurt more than larger ones, and the paper does not report further hyperparameter search or systems-level cost. Its efficiency claim is therefore a model-size proxy, not a wall-clock result.

现有 LLM agent 会把过去经验写成 skill memory，但很多方法把整条任务轨迹压成一条 skill，结果过度贴合源任务，后续检索时常成了噪声，甚至把性能拉低。作者要问的不是“能不能记忆”，而是“哪种诱导方式真的能跨任务复用”。

关键动作是把两个维度拆开：诱导粒度是 task-level 还是 subtask-level，存储格式是 text 还是 code。任务级 agent 把整条 ReAct 轨迹压成一个 skill；子任务级 agent 先分解子任务，再由 planner/executor/summarizer 轮转，每个 sub-trajectory 产出一条 skill。两类 memory 用同一 prompt、同一检索器，只比较 skill 本身；再定义 $utility(s)=specificity(s)\cdot abstractness(s)$。

作者在 AppWorld、OfficeBench、KramaBench 上跑了 11 个模型。结果很一致：task-level skills 平均伤害表现，Text 让 success 下降 $1.2$ 点，Code 下降 $4.1$ 点；subtask-level skills 则稳定增益，Text 提升 $1.9$ 点，Code 提升 $0.5$ 点。总体上，subtask-level 平均 $24.8\%$，高于 task-level 的 $22.1\%$；Text 也普遍优于 Code。

这篇工作的价值在于，它把“记忆有没有用”改写成“记忆怎样才有用”，而且 utility 不需要实际执行就能算出来。边界也很清楚：只测了三个长程基准，memory 是固定 induction/retrieval/dedup 规则，且只看最终状态，没法分析中间决策。

LLM agents can turn past trajectories into skill memory, but whole-trajectory skills often become source-task replicas. When retrieved later, they are noisy or misaligned context that can drag performance below a no-memory baseline. The real question is not whether memory exists, but which kind of induced skill actually transfers.

The paper isolates two axes: induction level and storage format. A task-level agent induces one skill from an entire ReAct trajectory. A subtask-level agent decomposes the task, runs a planner/executor/summarizer cycle, and emits one skill per subtrajectory. Each skill is stored as text or code, but both levels share the same prompt and retrieval pipeline. The authors then define skill utility as $utility(s)=specificity(s)\cdot abstractness(s)$, aiming to capture both match to real tasks and breadth of reuse.

They test this on AppWorld, OfficeBench, and KramaBench with 11 open-weight and proprietary models. The pattern is stable: task-level skills usually hurt, lowering average success by 1.2 points with text and 4.1 with code, while subtask-level skills help, improving success by 1.9 and 0.5 points. Across all 11 models and the three benchmarks, the average success is 24.8% for subtask-level versus 22.1% for task-level. Text transfers better than code at both levels, and the cost curves in the latency/dependency analysis cross in favor of subtask-level skills once the budget is no longer tiny.

The useful part is the diagnostic. Utility, which is execution-free, tracks both task success and actual reuse density in the stream, so it can screen a skill memory before you spend on deployment. The caveat is scope: the study stays within three long-horizon benchmarks, fixed memory rules, and final-state grading, so it does not yet tell us how the result behaves in computer use, coding, or evolving memories.

Tool use fails less at making the call than at recognizing when a tool applies, extracting arguments from messy context, composing multi-step workflows, and recovering when information is missing. MidTool moves that shaping earlier, into mid-training. It starts from web, PDF, code, and structured tool artifacts, then synthesizes supervision through two branches.
